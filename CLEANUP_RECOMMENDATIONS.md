# Cleanup Recommendations

A working list of accumulated improvements: known bugs, code smells, and future-work items. Each entry names the location, the problem, the suggested fix, and a rough severity to help triage when the time comes.

Severity legend:
- **🐛 Bug** — wrong behavior; a real user will hit this
- **🩹 Smell** — works but is fragile, misleading, or unidiomatic
- **🔭 Future** — not committed to, but a known-better path

---

## Future work

- **🔭 Distribute the libraries as NuGet packages.** Internal consumers take Keri by project reference today, which means vendoring the source into their solution; packaging would let an app depend on a pinned, versioned `Keri.*` instead. Three projects are packable — `RESTServices`, `EpicorSvcs`, and `FileHandling`; the executables (`KeriConfigurator`, `EpicorSvcDemo`, `EpicorSvcPOCs`) and the test project are not. The design choice is one package or several: packing them separately — say `Keri.RestServices`, `Keri.Epicor` (depending on it), and `Keri.FileHandling` — preserves the vendor-neutral boundary the codebase has deliberately guarded, so a transport-only consumer can take `RestServices` alone, whereas a single umbrella package is simpler to consume but recouples the neutral transport to Epicor; the layered split is the more principled path. Three existing decisions make this low-friction: the libraries already multi-target, so `dotnet pack` emits `lib/net48/` and `lib/net8.0/` in one package each; per-project versioning maps straight onto per-package versions, with the `Project-vX.Y.Z` tags a natural publish trigger; and the 0.3.0 config-free refactor keeps `App.config` and `KeriConfigurator` out of the libraries, so no configuration baggage rides along — a package consumer constructs the client programmatically from an `EpicorRESTSessionKey`. The remaining work is mostly metadata and a feed: fill `PackageId` / `Authors` / license / `RepositoryUrl` / tags (the `Company` field is currently empty), let `dotnet pack` turn the inter-project references and existing NuGet dependencies (Newtonsoft.Json; MailKit and `System.Configuration.ConfigurationManager` on net8.0) into package dependencies, and choose a feed. Since the repo is private with no external consumers, that feed is GitHub Packages — the repo already lives on GitHub — or a local folder feed, not nuget.org; a `dotnet pack` step (optionally pushing on the per-project tags) slots into the existing `ci.yml`.

- **🔭 Offline coverage for the `{ENV:NAME}` resolution logic (KeriConfigurator 0.5.0).** The token feature shipped without automated tests — its correctness currently rests on running the configurator and watching a live call resolve. The resolution core is pure and deterministic, so it is a clean fit for the offline xUnit suite. `KeriConfig.Resolve` and `IsEnvToken` are `internal`, so reaching them needs a `ProjectReference` from `KineticRESTIntegrator.Tests` to `KeriConfigurator` plus `[assembly: InternalsVisibleTo("KineticRESTIntegrator.Tests")]` on KeriConfigurator (the test project references only `EpicorSvcs` today). Once exposed, cover: `Resolve` mapping a set token to its environment value, an unset token to empty, a literal straight through, and a `YOUR_*`/blank placeholder to empty; and `IsEnvToken` accepting a well-formed `{ENV:NAME}` (emitting the name) while rejecting a malformed or non-token value. The validation behavior — `ValidateSettings` naming the unset referenced variable in its error — is harder to unit-test directly: `ValidateSettings` is `private`, reached only through the public `BuildSession()`, which reads ambient `Properties.Settings` / `App.config`. Either drive `BuildSession()` with settings whose token points at an unset variable (an integration-flavored test that sets `Settings.Default` values at runtime), or make the seam test-friendly — promote `ValidateSettings` to `internal`, or split the resolve-and-validate core so it takes values as parameters instead of reading ambient config. One xUnit gotcha to plan for: environment variables are process-global and xUnit runs test classes in parallel, so any test that sets a variable must set and clear it within the test (a `try`/`finally` or an `IDisposable` fixture), and the env-touching tests should share one test class or a non-parallel collection so they do not race each other. These slot straight into the existing `ci.yml` (it already builds and runs the offline suite on `windows-latest`), and the pre-commit hook will nudge the README test count up on its own once they land. This is the one real coverage gap behind the 0.5.0 release.

- **🔭 Pagination for the OData entity-set reads.** The entity-set methods (`POesAsync`, `PartsAsync`, `PODetailsAsync`, and so on in the OData service wrappers) accept `top` (page size) but expose no offset, so a caller can cap the first page but cannot walk past it. Add `$skip` (offset) and a way to detect the last page — either `$count=true` on the first call, or treating “fewer than `top` rows returned” as end-of-data — most naturally as an iterator / `IAsyncEnumerable<T>` wrapper so callers loop pages without managing skip arithmetic. This applies to the same v2 OData methods the `SelectFor<T>()` / `additionalColumns` work touches and is independent of it (column trimming is row *width*; pagination is row *count*). The `SelectFor<T>()` / `additionalColumns` work has since shipped in 0.4.1, leaving pagination as the remaining row-axis gap. Only meaningful on an API-key (v2 OData) session; a Basic-auth (v1) session ignores `$skip` just as it ignores `$select` / `$top`.

- **🩹 OData query options are silently ignored on a v1 (Basic-auth) session.** `SelectFor<T>()` / `$select`, `additionalColumns`, `top`, and `filters` are OData query options honored only on the v2 OData endpoint, which Keri selects when the session carries an API key (`KeyType == "apikey"`). On a Basic-auth (v1) session the transport appends these options to a v1 URL where the server drops them, returning the full untrimmed collection with no error — a silent no-op that looks like the option “didn’t work.” Currently handled by documentation only (the `SelectFor` XML doc and the read-behavior docs note the v2 requirement). Consider detecting the Basic posture plus supplied OData params and emitting a warning so the no-op is visible — but do not throw: a no-op should not become a hard failure, and a v1 caller passing `top` is not an error, just unsupported. Detection would live at the transport or service-method boundary where the URL modifier is known.

- **🔭 Convenience write helper: `EditAsync(id, dto => { ... })`.** A multi-table BO edit is currently a manual round-trip — `GetByID` to fetch the whole dataset, mutate the typed row(s) and any `ExtraData["…_c"]` entries, set `RowMod`, then `Update`. A helper that wraps that sequence (`GetByID` → apply the caller's mutation lambda → `Update`) would remove the boilerplate for the common single-record edit while leaving the explicit path available for multi-table or multi-step edits. Only sketched, not committed — add it if a real call site makes the round-trip repetitive enough to justify the surface.

## Recently addressed (kept here briefly as project history)

- **Environment-variable references in configuration — shipped in KeriConfigurator 0.5.0.** The 0.3.0 refactor removed the old implicit `EPICOR_*` override; this reintroduces environment variables in an explicit form. Any `App.config` value may be written as `{ENV:NAME}` and is resolved from the environment by `KeriConfig` at build time — a literal is used as-is, and the environment is read only where a value is a token, so there is no hidden precedence. KeriConfigurator's console offers a `[V]alue` / `[E]nv-reference` choice on the three secrets (Epicor password, API key, SMTP password) and writes the token instead of the secret; the live connection test and validation resolve the same way, naming an unset referenced variable. Docs updated: CONFIGURATION.md gains a dedicated section, and README and `App.config.template` were updated. See the `KeriConfigurator 0.5.0` block in `CHANGELOG.md`.

- **DTO-driven `$select` with `additionalColumns` — shipped in 0.4.1.** Each OData entity-set read previously carried a private `default*Select` list applied as `$select` when the caller passed none; a list narrower than its DTO left the un-selected typed properties null on every returned row even though the data existed. Replaced across all twelve entity-set services (20 read methods) with `EpicorSvc.SelectFor<T>()`, which reflects the row DTO's public properties — skipping the `[JsonExtensionData]` overflow and `[JsonIgnore]` members, honoring `[JsonProperty]` names, cached per type — into the default `$select`, so the request mirrors the DTO and every typed property is populated. A new `additionalColumns` parameter appends columns the DTO doesn't model (install-specific `_c` columns, Epicor UD placeholder columns) onto the select; they arrive in the row's `ExtraData` overflow. The existing `select` parameter is unchanged — a full override that doubles as a lean-projection lever. The 20 `default*Select` lists were deleted; offline `SelectForTests` cover the reflection rules. These OData options are honored only on a v2 (API-key) session — see the two related Future-work items above. See the `[0.4.1]` block in `CHANGELOG.md`.

- **Renamed the misleading `DynamicURLModifier_OAuth` field to `DynamicURLModifier_Keyed`.** On `RESTAuthenticationObject` (`RESTServices`), the URL modifier applied when a connection authenticates with a key/token (rather than HTTP Basic) was named `_OAuth` — misleading, since it has nothing to do with OAuth and is selected by `KeyType == "apikey"`. Renamed to `_Keyed` to name the generic auth-posture route ("the route used when the connection is keyed") rather than a specific credential or protocol. `_ApiKey` was considered but rejected as naming the credential rather than the route; `_V1`/`_V2` rejected as Epicor-specific versioning vocabulary leaking into the vendor-neutral transport. The paired `DynamicURLModifier_Basic` was already well-named and is unchanged. Done via a semantic rename across `RESTAuthenticationObject`, the `DynamicURLModifier` selector, and the `EpicorSvc` constructor, plus the `EXAMPLES_RESTAPI.md` references. In-solution-only public rename — patch-level under the versioning policy.

- **Epicor structured error feedback — shipped in 0.4.0.** The former Future-work item (transport flattening the whole HTTP error into one `ErrorMessage` string, a perpetually-null `StatusCode`, and no `ErrorType`/`CorrelationId`) shipped largely as designed. `RESTServices` stayed vendor-neutral: on an HTTP error, `RESTConnect` now emits `statusCode` (numeric), `reasonPhrase`, and `httpResponseBody` (the raw body, verbatim) as fields alongside the generic `ErrorMessage`. `EpicorSvcs` parses Epicor's flat error envelope in `ToOperationResult` — clean `ErrorMessage`, first-class `ErrorType` and `CorrelationId`, status from the numeric field (falling back to the body's `HttpStatus`), with the parsed envelope (including `ErrorDetails`) kept in `RawResponse`. `UDTableSvc.IsRecordNotFound` now keys on `ErrorType == "Ice.Common.RecordNotFoundException"` (with a bare-404 fallback) instead of the status/text sniff. The demo and POCs print `CorrelationId` on failure. Two deviations from the original sketch: the transport hands data up via neutral `JObject` properties (`statusCode` / `httpResponseBody`) rather than a new result type — the lower-churn option named in the open design question — and no `ErrorSummary` computed getter was added (printing `ErrorMessage` + `CorrelationId` covered the need). *Breaking* as predicted: `ErrorMessage` content changed from the verbose blob to Epicor's clean text. Rode 0.4.0 alongside the `RESTServices` `RESTHttpClient` → `RESTConnect` collapse and the `KeriConfig.CreateClient` → `BuildEpicorClient` rename. See the `[0.4.0]` block in `CHANGELOG.md`.

- **Configuration refactor — shipped in 0.3.0.** Configuration moved out of the libraries into a dedicated composition root, `KeriConfigurator`, which owns the unified settings schema (connection + email), the single shared `App.config` (consumed by the executables via `<AppConfig>`), and the factories `KeriConfig.BuildEpicorClient()` / `KeriConfig.BuildSmtpSettings()`. `EpicorSvcs` and `FileHandling` are now configuration-free: `EpicorClient.FromConfiguration()`, `EpicorConfiguration`, `SmtpSettings.FromConfiguration()`, both per-library `Settings` schemas, the net8 `ConfigurationManager` packages, and the per-project `App.config` seeding were all removed. `SmtpSettings` became public and `FileProcessing.EmailReport` takes it. The console gained per-field revisit, a live connection test (`EpicorClient.TestConnectionAsync`), and an SMTP reachability test (`Emailer.TestConnection`). Environment-variable configuration (`EPICOR_*`) was removed; off-disk secrets use a programmatic `EpicorRESTSessionKey`. See the `[0.3.0]` block in `CHANGELOG.md`.

- **CI — GitHub Actions build + offline tests on push and PR.** A `ci.yml` workflow at `.github/workflows/` builds the solution and runs the offline test suite on `windows-latest` (which carries the .NET Framework 4.8 reference assemblies the `net48` target needs) on every push and pull request to `main`. It seeds a placeholder `App.config` from the template before building, so the demo's seed-then-fail-the-build target — which fires on a fresh checkout — doesn't trip CI; the offline tests need no real connection values. This was Future-work #1.

- **Services made session-only — shipped in 0.2.4.** The `EpicorSvc(string env)` constructor and the matching `(string env)` constructor on all 23 service classes were removed; services are now built only from an `EpicorRESTSessionKey`, and configuration is read in exactly one place (`EpicorConfiguration.BuildSession()` / `EpicorClient.FromConfiguration()`). This was Future-work #2 and completes the config-agnostic boundary begun in 0.2.3 — a service no longer reaches into config as a side effect of construction. A repo-wide check confirmed every direct service construction (the `EpicorClient` facade, service-to-service calls) already passed a session, so nothing downstream broke. *Breaking (source):* `new PartSvc("pilot")` no longer compiles; build a session via `BuildSession(env)` or go through `FromConfiguration(env)` and the facade.

- **Configuration loading made explicit across both libraries — shipped in 0.2.3.** Reading `App.config` / environment variables moved out of constructor and field-initializer side effects into named factories. `EpicorClient.FromConfiguration(env)` replaced `new EpicorClient()`, with the read/validate logic centralized in the new `EpicorConfiguration` class (the parameterless/`(env)` client constructor was removed; the demo and `EpicorSvcPOCs` moved to `FromConfiguration`). In FileHandling, `SmtpSettings.FromConfiguration()` replaced the per-field `Settings.Default.*` initializers and `FileProcessing.EmailReport` now loads SMTP settings plus the developer-recipient address explicitly — making `EmailReport` the single config-read point for the email path. A codebase check confirmed nothing built `EmailSpecs` or called `Emailer.Send` outside `EmailReport`, so neutralizing the implicit defaults stranded no caller. FileHandling synced to 0.2.3 to match EpicorSvcs. The one remaining piece — removing the `EpicorSvc(string env)` service constructor — shipped in 0.2.4 (see below).

- **Typed-DTO API for UD-table access, plus surrounding service/method renames — shipped in 0.2.0.** The feature design was outlined here at length earlier in the cycle (one of the longer Future-work entries this document has ever carried) and shipped across nine commits on `feature/typed-dto-mapping`. End state: `UDTableSvc.SaveAsync<T>`, `GetByIDAsync<T>`, and `QueryAsync<T>` let callers define a typed DTO for a UD-table use case, decorate properties with `[UDTableColumn("Key1")]` / `[UDTableColumn("ShortChar03")]` etc., and round-trip rows as their own type instead of the generic `UDRow`. Validation at first use, capacity checks before save, auto-emitted `Character10` column-legend when the DTO doesn't own that column, and ExtraData round-tripping for install-specific `_c` custom columns when the DTO declares an `[JsonExtensionData] IDictionary<string, JToken>` property. Surrounding renames: `UDXSvc` → `UDTableSvc`, `EpicorClient.UDX` → `EpicorClient.UDTable`, `UdxPoc` → `UDTablePoc`, `GetAllAsync` → `QueryAsync`, `DeleteAllAsync` → `TruncateAsync` (with pre-prod/POC framing). `GetByIDAsync` rewritten to call Epicor's real `GetByID` BO action (single round trip with query parameters) instead of the previous OData filtered-read approximation; return type narrowed from `List<UDRow>` to `UDRow`. Also: `UDRow.Key1` lost its placeholder default (now null, forcing the caller to set it); `Number20` "checksum" reservation dropped from documentation; the column-allowlist in `UDXSvc` write/read paths replaced with a property-exclusion approach that lets `ExtraData` `_c` columns flow through. Added 56 new tests (108 total). See the `[0.2.0]` block in `CHANGELOG.md` for the full per-change rundown and migration notes.

- **Comment-conventions polish across the codebase.** Addressed three things in one sweep. Section-comment dividers (`// ---` blocks) added to three services that had been navigating-by-indent: `PartSvc` (2 dividers), `UDXSvc` (3 dividers — including a "destructive operations" section for the delete paths), and `VendorSvc` (2 dividers, with a small accompanying method reorder so OData wrappers and BO action wrappers form contiguous groups). The audit also surfaced that `MenuSvc` — flagged in the earlier "section-comment standardization" entry — actually doesn't need dividers; its four methods are two generic+typed overload pairs in a single conceptual group. The same audit caught three more stale `<see cref>` references that the earlier rename-batch doc sweep missed: `Dtos/OrderHed.cs` (pointed at the renamed `FindOrderByPONumAsync`), `Platform/ProjectSvc.cs` (three references to the renamed `NewProjectAsync`), and `Sales/SalesOrderSvc.cs` (stale orchestrator names in its class-level remark). And: `OperationResult<T>`'s three factory methods (`Success`, `Failure` × 2) gained complete `<param>` and `<returns>` XML documentation, closing the last gap in the codebase — 116/116 public methods now carry complete XML docs. Companion to the comment-conventions work, `EpicorClient` was marked `sealed` to make its facade-pattern intent compiler-enforced: consumers extending the client should use composition, not inheritance.

- **`FileHandling` build warnings silenced.** Four MSB3277 warnings on `net48` (BCL facade vs. `ClosedXML` netstandard2.0 transitive package versions) and four MSB3836 warnings on `net8.0` (autogenerated binding redirects overlapping with the hand-coded ones in `App.config`) suppressed via `<NoWarn>$(NoWarn);MSB3277;MSB3836</NoWarn>` in `FileHandling.csproj`. Both warnings describe states that the project deliberately handles (`App.config` binding redirects resolve the runtime side of the conflict); the suppression is documented with an explanatory comment alongside it so future readers can tell at a glance that this is known-benign rather than a hidden bug. Alternative fixes (explicit BCL-facade package pins, removing the App.config redirects) were attempted or considered and rejected as more invasive than the situation warrants.

- **Workflow naming convention sweep — `Create*` / `Add*` / `Get*` verbs throughout, no more inline URL building.** Eight orchestrator methods renamed: `NewProjectAsync` → `CreateProjectAsync`, `NewQuoteHedAsync` → `CreateQuoteAsync`, `NewOrderAsync` → `CreateOrderAsync`, `NewOrderLineAsync` → `AddOrderLineAsync`, `GetNewPartRevAsync` (workflow) → `AddPartRevAsync`, `BySearchWordAsync` → `GetPartsBySearchWordsAsync`, `FindOrderByPONumAsync` → `GetByPONumAsync`, `UDCodeLookUpAsync` → `GetUDCodeDescriptionAsync`. The verb conventions established: `Create*` for top-level entities (no parent), `Add*` for items added under an existing parent (tracked by whether the method takes a parent-id parameter), `Get*` for reads. `GetByPONumAsync` is a behavior change as well as a rename — it now returns the full `GetByID` dataset directly instead of a narrow OData list, replacing the previous two-call caller pattern. Structurally, four workflow methods that built Epicor URLs inline (`svc = "Erp.BO.PartSvc/Parts"` etc.) now call the public OData wrappers instead; `ChangePartUnitPriceAsync` moved out of workflows to `PartSvc.cs` because it's a BO wrapper whose name matches an Epicor BO method, not an orchestrator composing developer-facing operations. A new `GetNewPartRevAsync` BO wrapper landed on `PartSvc.cs` (template-fetch only, distinct from the workflow's create-and-persist `AddPartRevAsync`). `PartSvc.cs` method order also normalized to group writes together. POCs (`EpicorSvcPOCs/UserCodesPoc.cs`, `EpicorSvcPOCs/SalesOrderPoc.cs`) updated to call the renamed methods; three stale `<see cref>` references in DTOs that pointed at underscore-prefixed names also fixed in the same batch.

- **Repo-wide UTF-8 encoding cleanup — scope corrected to six broken files.** A prior entry in this document claimed twenty `.cs` files contained Windows-1252-encoded em-dashes. A strict UTF-8 decode of every `.cs` file turned up only six actually-broken files (10 stray 0x97 bytes total): `EpicorSvc.cs`, `AR/PayMethodSvc.cs`, `AR/PaymentEntrySvc.cs`, `Inventory/SerialNoSvc.cs`, `MasterData/SalesRepSvc.cs`, `Platform/GenxDataSvc.cs`. The other fourteen files had byte 0x80 or 0x94 — but only as the valid middle and last bytes of the proper three-byte UTF-8 em-dash sequence `\xE2\x80\x94`. Not broken at all, just visually surprising in a hex dump. The scope-overstatement is worth owning; it traced to a grep pattern that matched any high-bit byte without checking whether the byte was part of a valid UTF-8 sequence. The genuine breakage in the six files (each 0x97 byte replaced by the proper UTF-8 em-dash) is now fixed; every `.cs` file in the repo decodes cleanly as UTF-8.

- **OData entity-set wrappers — six new wrappers across five services, plus three DTOs.** `PayMethodsAsync` on `PayMethodSvc`, `PaymentEntriesAsync` on `PaymentEntrySvc`, `SerialNoesAsync` on `SerialNoSvc`, `MiscShipsAsync` on `MiscShipSvc`, and both `QuotesAsync` and `QuoteDtlsAsync` on `QuoteSvc`. All follow the standard shape (`filters` / `select` / `top` parameters with a practical-core default `$select`) and return `OperationResult<List<T>>` against the appropriate DTO. Entity-set names match Epicor's REST help exactly — `SerialNoes` (matching the `POes` pattern), `PaymentEntries` (matching `JobEntries`), `MiscShips` whose entity set returns `MscShpHd` rows (the header). Three DTOs landed alongside: the existing `QuoteHed` DTO expanded from 15 properties to ~50 (identity, dates, status flags, currency/terms, sales funnel, base-currency amounts on top of the existing write-side OTS fields); new `QuoteDtl` and `MscShpHd` DTOs with the same practical-core pattern. `InvTransferSvc` deliberately not included — its BO does not expose an OData entity-set wrapper.

- **`ReceiptSvc` shipped — fills the missing-receipts gap, completes the purchasing-to-receiving picture.** The 23rd service wrapper, in `EpicorSvcs/Purchasing/` alongside `POSvc`, exposes three OData entity-set wrappers (`ReceiptsAsync`, `RcvDtlsAsync`, `RcvHeadAttchesAsync`), five BO action wrappers (`GetByIDAsync`, `GetNewRcvHeadAsync`, `GetNewRcvHeadWithPONumAsync`, `GetNewRcvDtlAsync`, `GetNewRcvHeadAttchAsync`), and three DTOs (`RcvHead`, `RcvDtl`, `RcvHeadAttch`). The class is a partial declaration ready to host a `ReceiptSvc.Workflows.cs` file. The compound key (`vendorNum`, `purPoint`, `packSlip`) is passed as query parameters on `GetByIDAsync`. POC example deferred until the work can be verified against a real Epicor install.

- **`UpdateAsync` added to seven services — the write primitive across the practical-core write surface.** `CustomerSvc`, `JobEntrySvc`, `POSvc`, `ReceiptSvc`, `VendorSvc`, `SalesRepSvc`, and `PaymentEntrySvc` each gained an `UpdateAsync(JObject ds, CancellationToken ct)` method that posts a mutated dataset back to Epicor's `Update` endpoint. All seven have identical shape — they wrap the plain `Update` BO method (not `UpdateExt`), and the caller mutates rows in the dataset returned by `GetByIDAsync` before posting. Before this work the library had write primitives on `PartSvc` and `SalesOrderSvc` (as `MasterUpdate`) and a couple of others; the new methods bring writes to every service where the symmetry made sense.

- **`GetByIDAsync` added to `ProjectSvc` and `QuoteSvc` — read primitive completion.** Both services had `UpdateAsync` but no `GetByIDAsync`, an asymmetry that meant a caller could write a project or quote but not read one back through the service. Both methods follow the standard wide-dataset-as-`JObject` pattern, with docstrings pointing at the relevant DTO for header materialization.

- **`Customer` DTO expanded from 4-property starter to ~50 practical-core columns.** Previously the DTO modeled only `Company`/`CustNum`/`CustID`/`Name`. Expanded to cover identity, sold-to address, bill-to address, sales/shipping/terms defaults, and credit-control settings. `defaultCustomerSelect` in `CustomerSvc` widened to match so the default OData read populates the new columns automatically. Per-currency variants, computed totals, country-specific groups, and install-specific `_c` columns stay in `ExtraData` per the practical-core convention.

- **Method ordering normalized across five services to match the POSvc convention.** `PartSvc`, `SalesRepSvc`, `SalesOrderSvc`, `UDXSvc`, and `EngWorkBenchSvc` had accumulated ordering inconsistencies — `PartSvc` had `UpdateAsync` and `UpdateExtAsync` 83 lines apart with three unrelated methods between them; `UDXSvc` had `UpdateAsync` listed before any read methods; `SalesRepSvc` had `GetByID` before its OData wrapper; etc. All five reordered to the convention `POSvc` already follows: OData wrappers → reads → templates (parent before child) → write primitives → destructives where applicable → internals last. Pure reorder, no signature or behavior change.

- **`payload` parameter renamed to `ds` on public write methods across eight services.** A stylistic minority (7 uses across 5 files) was normalized to the codebase's dominant `ds` convention (now 37 uses across 10 files). The choice matches Epicor's own JSON envelope, where the top-level key on `Update` payloads is literally `"ds"`. Technically breaking for callers using named-argument syntax (`UpdateAsync(payload: ds)`); practically near-zero risk since positional argument syntax is universal for a first positional parameter. Two local variables in `PartSvc` deliberately kept the name `payload` — they're internal scratch JObjects, not API surface.

- **README examples corrected — two calls to `client.Customer.GetListAsync(...)` replaced.** Two examples in the README called a method that doesn't exist on `CustomerSvc` (`GetListAsync` lives on `PartSvc`, not `CustomerSvc`). The second example additionally assigned the return of `GetByIDAsync` to a `Customer` typed variable, which wouldn't compile. Both examples now use `CustomersAsync` with proper OData filter syntax. The README staleness items in the same fix pass: "twenty-two Epicor service wrappers" → "twenty-three" (line 39), "22 Epicor BOs" → "23 Epicor BOs" with Receipt added to the named list (line 60).

- **`POSvc` shipped — fills the missing-POs gap.** The 22nd service wrapper, in `EpicorSvcs/Purchasing/`, exposes three OData entity-set wrappers (`POesAsync`, `PODetailsAsync`, `PORelsAsync`), four BO action wrappers (`GetByIDAsync`, `GetNewPOHeaderAsync`, `GetNewPODetailAsync`, `GetNewPORelAsync`), and three DTOs (`POHeader`, `PODetail`, `PORel`). The class is a partial declaration ready to host a `POSvc.Workflows.cs` file when orchestrators (multi-line PO creation, drop-ship setup, etc.) become necessary. The OData entity set is `POes` (Epicor's unusual plural — same naming convention that gave us `JobEntries`). Two design notes worth surfacing: there is no `GetNextPONum` action because Epicor auto-assigns the number when `POHeader` is saved with `PONum = 0`, so the auto-numbering happens inside the create flow rather than as a separate call; and `PODetail` exposes the PO number as `PONUM` (all caps) where its sibling tables use `PONum` — the DTO matches Epicor's casing exactly because the JSON deserializer is case-sensitive, the mismatch is on Epicor's side. POC example deferred until the work can be verified against a real Epicor install.

- **`JobEntrySvc` shipped — fills the missing-jobs gap.** The 21st service wrapper, in `EpicorSvcs/Production/`, exposes four OData entity-set wrappers (`JobEntriesAsync`, `JobAsmblsAsync`, `JobMtlsAsync`, `JobPartsAsync`), three BO action wrappers (`GetByIDAsync`, `GetNewJobHeadAsync`, `GetNextJobNumAsync`), and four DTOs (`JobHead`, `JobAsmbl`, `JobMtl`, `JobPart`). The class is a partial declaration ready to host a `JobEntrySvc.Workflows.cs` file when orchestrators (release/close/complete) become necessary. The OData entity set is `JobEntries` (not `JobHeads`) per Epicor's REST help, and `JobHead` notably uses the `UserChar`/`UserDate`/`UserDecimal`/`UserInteger` UD column series rather than the `Character01`/`Number01`/`CheckBox01`/`ShortChar01` series used on most other Epicor tables. `JobAsmbl` and `JobMtl` deliberately omit the large `TLA`/`TLE`/`LLA`/`LLE` cost-rollup variants and `Carbon*` emissions-tracking variants — they remain accessible via `ExtraData` if needed. POC example deferred until the work can be verified against a real Epicor install.

- **`Company` moved off `RESTSessionKey` and into `EpicorRESTSessionKey`** — the vendor-agnostic transport layer no longer carries an Epicor concept. `Company` lives on a new `EpicorRESTSessionKey` subclass in `EpicorSvcs.Dtos`, `RESTServices` is now genuinely vendor-neutral, and the Epicor service and client constructors take the subclass. A note on versioning: this is a breaking API change and the original recommendation was to hold it for a deliberate `0.2.0`. In practice it landed in `0.1.1` with a `### Changed` changelog entry, because `0.1.1` was still unreleased and contained other breaking changes already (the UDX delete-method hardening below), so a single coordinated breaking pre-1.0 patch was the cheaper path than carrying two breakage milestones.

- **`UDXSvc` delete-method risk-mitigation** — the destructive paths previously fell back to `UDTableDefault` when no table was named, so a delete with a missing argument silently acted on whichever table the default pointed at. Fixed across the three delete paths: `DeleteByIDAsync` lost its `UDTable = null` default and is now required; `DeleteAllAsync` already required the table but now resolves it strictly with no `UDTableDefault` fallback; `UpdateAsync(..., delete: true)` now also resolves strictly. A null/empty/whitespace table throws `ArgumentException` before any rows are touched. `DeleteAllAsync` additionally gained a required `confirmDeleteAllRows` parameter, gating whole-table clears behind explicit, named-argument intent.

- **Deletion examples in `EXAMPLES_EPICOR.md` use a placeholder table name** — the deletion code block previously used `"UD22"`, a real Epicor UD table; a reader copy-pasting straight from the docs could have run a delete against their actual `UD22`. Changed to `"UDXX"`, with an inline comment marking it as a placeholder. The upsert example (line 96) still uses `"UD22"` since it's a legitimate "here's how you target a table" demonstration and a stray paste-and-run is non-destructive there.

- **`ConvertJArrayToCSV` empty-array bug fixed** — `FileHandling.ConvertJArrayToCSV` read column names from `data[0]` without guarding for an empty `JArray`, throwing `ArgumentOutOfRangeException`. It now returns an empty string for null or empty input, matching the already-guarded `ConvertJArrayToHTMLTable`.

- **`Menu.cs` DTO column name** — was `Seq`, now `Sequence` (matches Epicor's actual column; the `Seq` version silently zero-bound on `GetRowsAsync<Menu>`).
- **`UDRow.Date20` nullability** — was non-nullable `DateTime`, now `DateTime?`, accommodating legacy rows in Epicor that pre-date the always-stamp convention.
- **`OperationResult<T>.ExtractDto` empty-table handling** — previously threw `IndexOutOfRangeException` on an empty `ds[tableName]` array; now returns `default(T)` per the documented contract.
- **`EpicorSvcDemo/Program.cs` failure-then-continue** — previously called `JArray.FromObject(baqResult.Value)` even when the BAQ failed, throwing on the null `Value`; now early-returns on `IsFailure`.
- **`App.config.template` URLs** — previously stale on-prem pattern (`erp.example.com/ERP_Prod`); now SaaS-shape (`company-live.example.com/server`) matching the README's examples.
- **`_c` column audit across DTOs** — install-specific custom columns (`*_c`) were swept out of all shipped DTOs, restoring the practical-core promise that the library ships only columns every Epicor install has. Per-install custom columns remain accessible via `OperationResult.RawResponse`.
- **Audience-based public/internal classification across 6 services** — `EngWorkBenchSvc`, `InvTransferSvc`, `MiscShipSvc`, `QuoteSvc`, `ProjectSvc`, and `SalesOrderSvc` had a mix of public wrappers returning raw `Task<JObject>` and `public async Task<OperationResult<T>>` orchestrators. Reclassified per a consistent rule: generic CRUD verbs (`GetByID`, `GetNew*`, `Update`, table-name reads) are public and return `OperationResult<T>`; process-step helpers (`CheckOut`, `OnChange*`, `*RowMod`, `GroupUnLock`, etc.) are `internal` and return raw `JObject`. The public API now uniformly returns `OperationResult<T>`.
- **`EngWorkBenchSvc.AddMtlsAsync` null-deref hazard** — orchestrator called `GenerateGroupAsync`, then used `generated.Value` without checking `IsFailure`. On failure, the next line dereferenced a null `JObject`. Fixed during the EngWorkBenchSvc reclassification by adding the standard `IsFailure` propagation pattern.
- **Missing `HandleResponse` on six wrapper methods** — `EngWorkBenchSvc.UpdateAsync` and `ECOMtlsAsync` called bare `RESTCallAsync` without normalizing the response shape; `SalesOrderSvc.ChangeSellingQtyMasterAsync` did the same; `EngWorkBenchSvc`'s three internal process-step methods (`CheckOutAsync`, `ApproveAndCheckInAllAsync`, `GroupUnLockAsync`) also missed the wrapping. All six fixed for consistency. Epicor's structured error responses now surface through `ds["ErrorMessage"]` on every call.
- **Orchestrator identity-transform cleanup** — several orchestrators ended with `response.ToOperationResult(r => r)` — an identity transform that made sense when the underlying wrapper returned raw `JObject`, but became unnecessary once the wrappers themselves returned `OperationResult<T>`. Replaced with direct `return await UpdateAsync(...)` patterns where possible, or `OperationResult<T>.Success(...)` when constructing fresh results.
- **`FileProcessing.EmailDataReport` removed** — was a demo-shaped public method that silently overrode caller-set `Subject` and `Body`, a misleading API where the caller could not actually control what was sent. Deleted from the library; `EpicorSvcDemo/Program.cs` (the only known caller) updated to construct its subject and body inline and call `EmailReport` directly. `EMailMeta.RecipientName` preserved as a public DTO property to avoid a breaking change.
- **`"EMPTY_DATASET"` magic string removed** — `WriteDataToExcelFile` used to return the literal string `"EMPTY_DATASET"` as if it were a file path when given null data; two callers string-compared against it. Replaced with a `null` `FileAddress` and `string.IsNullOrEmpty` checks. README troubleshooting entry rewritten symptom-first since the magic string is no longer a user-visible diagnostic.
- **31-character Excel sheet-name truncation fixed** — `CreateExcelFileFromDT` used to derive the worksheet name by searching the filename for today's date in `yyyyMMdd` or `yyyy-MM-dd` format to find a truncation cutoff. The logic was coincidentally correct for one filename pattern and silently broken for others, plus had an off-by-one bug. Replaced with deterministic logic: caller-supplied `SheetName` wins, otherwise derived from the filename; both paths normalized through a single helper that substitutes Excel's illegal characters (`: \ / ? * [ ]`) with underscores and truncates to 31 chars.
- **SMTP modernization with dual-path implementation** — `Emailer.DotNetEmail` renamed to `Emailer.Send` and rewritten as a dual-path method: `System.Net.Mail.SmtpClient` on .NET Framework, `MailKit.Net.Smtp.SmtpClient` 4.16.0+ on .NET 8.0+. Same public API, same configuration, same behavior on both targets. New optional settings: `SMTPPort`, `SMTPEnableSsl`, `SMTPUsername`, `SMTPPassword`. Default behavior preserved (anonymous, no TLS, port 25). Validation rejects port 25 + TLS and port 465 + TLS as misconfigurations on both targets. No MailKit dependency on net48 (avoiding the unpatched MailKit 3.x STARTTLS-injection CVE GHSA-9j88-vvj5-vhgr); MailKit 4.16.0 on net8.0 is patched.
- **Multi-target migration (net48 and net8.0)** — `RESTServices`, `EpicorSvcs`, and `FileHandling` now multi-target both .NET Framework 4.8 and .NET 8.0. Consumer projects (`EpicorSvcDemo`, `EpicorSvcPOCs`, tests) remain single-target net48. Conditional `System.Configuration.ConfigurationManager` 8.0.0 NuGet on net8.0 preserves `Properties.Settings.Default` and `App.config` behavior matching the built-in support on .NET Framework. Conditional `Microsoft.CSharp` Reference on net48 only. Dead `RestSharp` PackageReference and dead `System.Configuration` References cleaned up.
- **Transport error-detail improvement** — `RESTHttpClient`'s `HttpRequestException` handler previously surfaced only the generic outer message ("An error occurred while sending the request."); it now walks the `InnerException` chain so the real cause (DNS failure, connection refused, TLS error) is visible. The timeout handler reports the configured timeout duration rather than a generic cancellation message.
- **`FileHandling` code organization** — `ExcelParser` (a misnomer — the class both read and wrote Excel) split into `ExcelReader` and `ExcelWriter`, each named for what it does. Email DTOs (`EmailSpecs`, `EMailMeta`, `SmtpSettings`) moved to `FileHandling/Dtos/`, matching the `EpicorSvcs/Dtos/` convention. `Emailer.cs` trimmed to just the `Emailer` class.
